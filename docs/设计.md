# 设计

本文记录**跨需求**的架构取舍：为什么这样切、否决了哪些方案、边界在哪。单条需求的边界
写在 `docs/requirements/REQ-*.md`，不在这里重复。

状态：草稿 · 2026-11-15 · 对应 v0.0.1

## 1. 只取内核，重写前端

上游 `deepseek-harness` 自带一份完整 Web GUI：React 前端 82,766 行 TS/TSX，
通过 Typert Remote 协议（34 个 namespace，编译器生成的 TypeScript 契约）与 Host 通信。
Electron 壳 `apps/desktop` 只是把这份前端装进 Chromium。

我们要的是一份更小的东西：**agent 内核照用，界面自己写**。

### 否决：复用官方 Web 前端 + Tauri 外壳

最省力的路，两天能出包。否决理由：它解决不了「界面不是我们的」这个问题——
需求是重写 UI，而不是给它换个壳。

### 否决：复刻 Typert Remote 协议

功能面确实最全（设置、工作区、终端、插件市场全都有）。但代价是：

- 34 个 namespace 的 wire 契约要在 Rust 里重写一遍；
- 契约由 TypeScript 编译器在构建时生成，上游一改就要跟；
- 我们连一个可读的协议规范都没有，只有生成物。

同样的功能，用 Tauri 原生 + 一个窄协议就能做到，成本差一个数量级。

### 采用：SDK stdio 桥

内核提供 `dsh --profile sdk`，把整个 runtime 以 **newline-delimited JSON-RPC 2.0 over
stdio** 暴露给外部进程。协议本体 571 行，9 个客户端方法 + 6 个服务端通知，
上游给了 TypeScript 和 Python 两套参考实现。

这是官方为「另一个进程驱动内核」设计的接口，形态正好是我们要的：Rust 主进程是父进程，
内核是子进程，一条管道。

## 2. 三个已知缺口，以及为什么补法比补协议便宜

SDK 面只覆盖「对话」这件事。三个缺口在源码里核实过：

| 缺口 | 上游行为 | 我们的补法 |
| --- | --- | --- |
| 列历史会话 | 无此方法；`session/resume` 只恢复、**不重放历史事件** | 直读 `$DSH_HOME/sessions` 的 JSONL（`crates/dsh-store`） |
| 同一 runtime 换模型 | `initialize` 把 provider/model 钉死在实例字段上 | **每个模型一个 runtime 子进程**（`crates/dsh-runtime` 的池） |
| 设置 / 凭证 / 插件市场 | 走 Remote 面的 controller | 自己写，密钥经环境变量注入子进程 |

三条都是从「内核 / 客户端职责划分」自然长出来的，不是妥协。

### 会话日志：默认压缩，所以要么关压缩要么解压

`sessions/<group>/<id>/session.v4.jsonl.zstd`，默认 `compression: 'zstd'`。
上游明说压缩格式必须经它自己的 backend 读。我们只读不写，所以两条路：

- **A（当前选择）**：profile patch 把 `compression` 设成 `none`，Rust 直接读 NDJSON。
  代价是磁盘 3~5 倍。个人客户端可接受，省掉一个解码路径。
- B：`zstd` crate 流式解帧再按 `\n` 切。等 A 的磁盘占用成为真实问题时再换。

只读意味着**不需要复刻 v0→v4 的迁移链**：读到 `version != 4` 就标记「旧格式，不可读」，
不尝试翻译。

## 3. 模块边界

```
apps/desktop (React) ──invoke/listen──> apps/desktop/src-tauri (组装)
                                              │
                     ┌────────────────────────┼────────────────────────┐
                dsh-runtime              dsh-store               dsh-native
                     │                        │                        │
                  stdio                   磁盘 JSONL              pty / fs
                     │                        │                        │
                     └──────────── dsh 内核（Node，原样）─────────────┘
```

三条硬边界：

1. **`src-tauri` 只组装**。命令函数超过十行就说明逻辑该下沉到 crate。
2. **`dsh-store` 不依赖 `dsh-runtime`**。历史读取必须能脱离内核单独测。
3. **前端不碰 IO 路径**。所有文件系统访问经 `src/lib/ipc.ts`（tauri-specta 生成的绑定）。

`dsh-native` 有意做成独立 crate —— 它和 dsh 没有任何关系，将来可以整体搬走。

## 4. 为什么不多拆 frontend package

前端只有 `apps/desktop` 一个消费者。拆成 npm workspace 包的唯一收益是「将来可能复用」，
而成本是每次改代码都要跨包构建、路径别名、类型引用跳转。等真的出现第二个消费者再拆。

## 5. 类型不手抄

Rust 命令用 `tauri-specta` 生成 TypeScript 绑定。改一个 Rust 结构体，前端立刻类型报错——
这比手写两份接口然后靠人记得同步可靠得多。


## 内核改造：三层，从便宜到贵

内核 819 MB，不进仓库。但「不进仓库」不等于「不能改」——这是两件不同的事，混在一起会
得出「以后要改内核就完蛋了」这个错误结论。

| 层 | 改什么 | 升级后还在吗 | 住哪 |
| --- | --- | --- | --- |
| **插件** `bridge/` | 加行为：订阅事件、挂服务、开路由 | 在，除非事件形状变了 | 本仓库，通过 `profiles/sdk/cordis.patch.yml` 挂载 |
| **补丁** `kernel-patches/*.patch` | 改内核模块里的一行 | 不在，必须重基 | 本仓库，每次 `kernel:fetch` 自动应用 |
| **上游 PR** | 任何活过一个版本的东西 | 永久 | deepseek-ai/deepseek-harness |

顺序就是从便宜到贵。**现状：全部需求都停在第一层** —— 流式那一整套（订阅
`agent/assistant-stream`、stderr 标记行、Rust 侧解析）就是插件做到的，一行内核源码都没动。

### 为什么补丁失败要硬失败

半打过补丁的内核比没拉下来的内核更糟：它看起来能用，行为却和代码对不上，而且没人知道
是哪一半生效了。所以 `fetch-kernel.mjs` 里补丁应用失败 = 整个拉取失败，并打印是哪个文件。

### 否决的方案

- **把内核提交进仓库**：819 MB、两万多个文件，且每个版本都是全量替换。仓库会变成分发渠道，
  而不是源码。
- **往 `kernel/` 里手改**：下次 `kernel:fetch` 直接覆盖，改动静默消失。这一条必须写进
  AGENTS.md 的红线，因为它是唯一"看起来生效了"的错误做法。
- **fork 整个内核**：升级就是手工合并两万文件的分叉，代价远高于维护几个补丁。

## 版本号：不按提交数走

语义化版本描述的是「消费方需要知道的变更」。到目前为止没有任何人消费过任何一个版本，
所以按提交递增（一天从 0.1 到 0.12）不是进展，是提交计数器。

规矩：**只有真正交出去一个构建时才升版本**（打标签、出安装包、留回滚点）；普通提交累积在
`CHANGELOG.md` 的 `Unreleased` 下。切版本时，累积的那一段变成一个带整体理由的版本。
### 分叉用复制，不用重放

`session_fork` 复制会话日志并重写 header，不把历史重新喂给模型。理由：

- **重放会花钱**，而且模型第二次说的话不会和第一次一样——那不是分叉，是重新问一遍。
- 副本要能被内核 resume，这一点**问过内核**（`tests/fork_resume.rs`）。为此发现三个坑：
  header 必须带 `type`；可选字段不能序列化成 `null`（严格 schema 判成"不是 header"）；
  副本必须落在父会话所在的项目目录（内核按 cwd 编码分组，放错组报"日志损坏"）。

### 图片在 Rust 侧校验，正文在内核侧收编

`session_prompt_blocks` 发的是内核的 `contentBlocks`。分工：

- **Rust 校验形状**：类型白名单、单张 8 MB / 合计 24 MB（按**解码后**字节）、base64 合法性。
  理由是把错误提前到"任何进程花掉一个 turn 之前"，并且错误信息可以说人话。
- **内核收编字节**：把它写进 `attachments/v1/objects/<sha256>`，块被改写成引用。
  我们从不自己写附件库——那是内核的存储格式，跟着版本变。

### 附件回收的两条保护

图片进了附件库就没人删。我们清，但只清**同时满足**两个条件的：

1. 没有任何会话日志提到它的 `sha256`。扫描是**字节扫描不是 JSON 解析**——解析不了的日志
   仍然算引用，因为"读不出来"不等于"没在用"。
2. 落盘超过 6 小时。内核是**先**收字节、**后**写日志，所以刚写好的对象"无人引用"是正常状态。

### 崩溃恢复是惰性的

内核死了以后不在后台立刻重启，而是**等下一次请求**（`ensure_ready`）：

- 后台重启会和用户的重启、退出、切换路由抢同一个池，行为难预测；
- 惰性重启的时机天然正确：没人在用的时候，内核死着也不影响任何人。

重启有上限（默认 120 秒内 5 次），超过就报错说清楚崩了几次。第一次重启**立即**执行——
安静很久之后崩一次不是崩溃循环，让人等半秒是另一个 bug。握手成功后计数清零。
### 预览给前缀，不给错误

大文件预览原来直接拒绝（`TooLarge`）。想清楚之后改了：**拒绝等于第一页也看不到**，而第一页
恰恰是所有人在找的东西。现在读前 256 KB 并标 `truncated`。

技术要点是**切在字符边界**：按字节截断必然切在多字节字符中间，严格解码就失败，预览会变成一墙
替换字符——这正是这个模块当初要解决的问题。所以 `decode_prefix` 只接受**不 lossy 的**解码结果，
否则回退一个字节再试（最多 4 次）。第一版接受了 lossy 结果，于是从不回退，测试当场抓到。

一条旧测试断言"大文件必须被拒绝"，也一起改了——**测试写的是当时的决定，不是物理定律**。
