## 决策变更记录

按时间顺序，记「当初怎么想、后来为什么改」。

| 决定 | 当初 | 现在 | 为什么改 |
| --- | --- | --- | --- |
| 大文件预览 | 超过 256 KB 直接拒绝 | 给前缀 + `truncated` 标记 | 拒绝等于第一页也看不到，而第一页正是要看的 |
| 版本号 | 每个功能一提交就升版本 | 只在真交付时升，平时进 `Unreleased` | 一天从 0.1 跳到 0.12 不是进度，是提交计数器 |
| 内核改动 | 想直接改 `kernel/` | 插件 → patch → 上游 PR 三层 | `kernel/` 每次 fetch 会被覆盖，手改必然静默丢失 |
| 分叉语义 | 打算重放历史给模型 | 复制日志 + 重写 header | 重放要花钱，且模型第二次说的话不会一样 |
| 崩溃重启 | 打算后台立刻重启 | 惰性：下一次请求时重启 | 后台重启会和用户自己的重启/切路由/退出抢同一个池 |
| 附件回收 | 没做 | 清无人引用 + 6 小时宽限 | 内核从不删附件，删会话也不带走图片 |

## 对内核的四个错误假设（都是抓包纠正的）

1. **SDK 没有流式** → 对，所以才有 `bridge/` 把 Cordis 事件写成带前缀的 stderr 行。
2. **审批请求是通知** → 错，是**请求**，必须应答；而且 id 是字符串 `req_<uuid>`，不是数字。
3. **`session/prompt` 会复用已有会话** → 错，它**创建**会话，已存在就报 `already exists`。
4. **复制一份会话日志就能被内核读** → 不完整：header 必须带 `type`、可选字段不能序列化成
   `null`、副本必须落在父会话所在的项目目录。这三条都是被真内核拒绝后才发现的。
