# 接口

给要写 UI 的人看的契约。**✅ = 已经接好并跑过，⬜ = 内核有、我们没接。**

三层的边界：

```
前端（React）  ──invoke/event──▶  apps/desktop/src-tauri（装配层）  ──JSON-RPC over stdio──▶  内核
                                        │
                                        └── crates/dsh-runtime（进程与协议）
                                            crates/dsh-store（会话日志）
                                            crates/dsh-native（PTY、文件树）
```

前端只认两样东西：`invoke('<命令>')` 与 `listen('<事件>')`。**不要直接碰内核协议** ——
JSON-RPC 的帧形状由 `crates/dsh-runtime` 统一翻译成下面的 `KernelFrame`。

## 一、Tauri 命令（前端 → Rust）

签名都在 `apps/desktop/src/lib/ipc.ts`（`ipc` 对象）。全部 ✅。

### 应用与内核

| 命令 | 参数 | 返回 | 说明 |
| --- | --- | --- | --- |
| `app_info` | — | `{name, version}` | 版本号，用于关于页 |
| `kernel_paths` | — | `KernelPaths` | 内核装没装、装在哪 |
| `kernel_start` | — | `KernelStarted` | 启动**当前路由**的内核；同路由复用 |
| `kernel_initialize` | `{cwd, provider, model, reasoningEffort?}` | `unknown`（内核 serverInfo） | 握手；成功后该路由成为「新会话的路由」 |
| `kernel_route_switch` | `{provider, model}` | `{provider, model}` | 换模型不重启：起/复用该路由的内核并握手，旧内核继续跑 |
| `kernel_call` | `{method, params, timeoutMs?}` | `unknown` | 任意 SDK 方法的通用门（见第三节） |
| `kernel_answer` | `{id: FrameId, result}` | — | **应答内核请求**（审批、提问）。`id` 可能是字符串，别当数字 |
| `kernel_diagnostics` | — | `string[]` | 内核 stderr 尾部。当前实现恒返回空数组 |
| `kernel_stop` | — | — | 关掉池里**全部**内核 |

```ts
interface KernelPaths { home: string; kernelDir: string; entry: string; fetched: boolean; autoStart: boolean }
interface KernelStarted { pid: number | null; provider: string | null; model: string | null }
```

> `kernel_start` 与 `kernel_initialize` 都会走进程池：不同 provider/model 是**不同进程**。
> 想换模型又不想丢当前会话，用 `kernel_route_switch`。

### 会话（读的是内核自己的日志，不经协议）

| 命令 | 参数 | 返回 | 说明 |
| --- | --- | --- | --- |
| `session_list` | — | `SessionSummary[]` | 磁盘上全部会话，按更新时间倒序 |
| `session_load` | `{id}` | `SessionHistory` | 一条会话的全部 durable 事件，可直接喂 reducer |
| `session_search` | `{query, limit?}` | `SearchHit[]` | 跨会话**正文**搜索（扫描，不是索引） |
| `session_rename` | `{id, title}` | — | 只写客户端 overlay，不改内核日志 |
| `session_delete` | `{id}` | — | **移进 `trash/`**，从所有列表消失但字节还在。可恢复 |
| `session_purge` | `{id}` | — | 真正删除，不可恢复。UI 上应该是第二层确认 |
| `session_export` | `{id}` | `string` | 渲染成 Markdown 返回 |
| `session_export_to` | `{id, path}` | — | 同上，直接写盘（配合保存对话框） |

```ts
interface SessionSummary {
  id: string; title: string; cwd: string | null
  createdAt: number; updatedAt: number        // 毫秒时间戳
  eventCount: number
  isSubagent: boolean
  parentId: string | null                      // 子代理会话的父会话
}

interface SessionHistory {
  header: { id: string; cwd?: string; createdAt: number }
  events: StoredEvent[]                        // {type, seq, time, data}
}

interface SearchHit { sessionId: string; title: string; seq: number; time: number; snippet: string }
```

## 二、Tauri 事件（Rust → 前端）

| 事件 | 载荷 | 状态 | 说明 |
| --- | --- | --- | --- |
| `kernel://message` | `KernelFrame` | ✅ | 内核 stdout 的每一帧（含实时流） |
| `kernel://lagged` | `number` | ✅ | 订阅跟不上时丢了多少帧 |
| `kernel://exit` | `{code, requested}` | ✅ | 某个内核退了 |
| `pty://data` | `{id, data}` | ✅ | 终端输出，**base64**（要 `atob` 成字节再喂 xterm） |
| `pty://exit` | `{id, code}` | ✅ | 终端结束 |

```ts
type KernelFrame =
  | { kind: 'notification'; method: string; params: unknown }
  | { kind: 'request'; id: number | string; method: string; params: unknown }
  | { kind: 'response'; id: number | string; payload: {status:'ok'} | {status:'err'; code; message; data} }
```

> **`request` 与 `notification` 必须分开处理**：忽略一个 `request` 会让内核一直阻塞在那一轮。

## 三、内核 JSON-RPC 请求（我们 → 内核）

走 `kernel_call`。**这 8 个是全部**（内核 `default:` 直接抛 unknown method）。

| 方法 | 参数 | 状态 | 我们怎么用 |
| --- | --- | --- | --- |
| `initialize` | `{cwd, provider, model, approvalRequests, capabilities, reasoningEffort?}` | ✅ | 握手，`kernel_initialize` |
| `session/prompt` | `{sessionId, contentBlocks}` | ✅ | 发消息。**立即返回 message id**，不是等回答 |
| `session/query` | `{sessionId, contentBlocks}` | ⬜ | 只读侧问答（不进对话历史），需要非空 contentBlocks |
| `session/resume` | `{sessionId}` | ✅（自动） | 续接磁盘上的既有会话。**`kernel_call` 会在 `session/prompt` / `session/query` 前自动调用一次**：新起的内核不认识侧栏里的旧会话，不 resume 就会拿同一个 id 另建一个。UI 不需要自己调 |
| `session/wait` | `{sessionId}` | ⬜ | 等这一轮结束再返回（做 CLI 式交互时有用） |
| `session/working-directory/get` | `{sessionId}` | ⬜ | 会话的工作目录 |
| `session/working-directory/set` | `{sessionId, path}` | ⬜ | 改会话工作目录（UI 可以做成「切换项目」） |
| `shutdown` | — | ⬜ | 优雅退出；我们现在直接 kill 进程 |

| 方法 | 参数 | 状态 | 应答形状 |
| --- | --- | --- | --- |

## 八、扩展点：内核侧插件（`bridge/`）

内核没有「订阅流式」的协议方法，所以流式靠一个**装在内核里的插件**：

- 包名 `dsh-desktop-live-bridge`，装到 `$DSH_HOME/node_modules/`（Node 从
  `$DSH_HOME/profiles/sdk/` 逐级向上解析；装到 `kernel/node_modules` 无效）
- 订阅 Cordis 全局事件 `agent/assistant-stream`（**必须 `{global:true}`**，否则只收到自己创建的 agent）
- 每帧写一行到 **stderr**，前缀 `\u0001DSH-LIVE `，Rust 侧解析成
  `notification: dsh-desktop/live-chunk`
- 挂载方式：`profiles/sdk/cordis.patch.yml` 里插一行

**改内核行为的三个层级**（从便宜到贵）：插件 → `kernel-patches/*.patch`（`fetch-kernel` 自动应用，失败即拉取失败）→ 上游 PR。详见 `AGENTS.md#Changing the kernel`。

## 十、给新 UI 的优先级建议

1. **先用 `session_list` + `session_load` + reducer 把历史读出来**（`hydrate(events)`），
   一套渲染同时服务历史和实时流——这是这个客户端最重要的一条设计。
2. `kernel://message` 里的 `request` 优先于一切：**弹窗不出现 = 内核卡住不走了**。
3. 流式是 `dsh-desktop/live-chunk`，durable 是 `session.event`；前者拼正文，后者定终态。
   **不要用 durable 覆盖流式已经拼好的 reasoning**（内核有时不发 reasoning 块）。
4. 想做多模型：`kernel_route_switch`，不要重启应用。
5. 想加持久化 UI 状态：`settings_set` 只存 provider/model；别的状态自己找地方，不要塞进去。

## 十一、运行期语义（不写 UI 也必须知道）

### 一个路由一个内核

`initialize` 把 provider/model 钉在**进程**上，没有"切换"这个调用。所以：

- 换模型 = `kernel_route_switch` → 起/复用一个新进程，**旧的继续跑**；
- 池里有会话绑定的内核**永不驱逐**（宁可超出容量），因为驱逐等于结束一个还开着的对话；
- 同路由复用同一个 `Arc<KernelClient>`，切回去不花钱。

### 内核死了会发生什么

进程退出会被**真正监听到**（每 200ms 轮询 `try_wait`，因为别处没有等待子进程的循环）：

1. `kernel://exit` 事件带 `{code, requested}` 发给前端；
2. 该路由从池里移除 —— 之后 `kernel_call` 会明确报 "the kernel is not running"，
   而不是往一个已关闭的 stdin 里扔请求（那会表现为永远转圈、没有报错）。

`requested: false` 就是崩溃，值得展示给用户；`requested: true` 是我们关的。

### 写文件：原子替换

客户端自己拥有的每个文件——`settings.json`、改名覆盖 `session-titles.json`、
`provider.env`——都通过 `dsh_store::write_atomic` 写：先写同目录的临时文件、`sync_all`，
再 `rename` 覆盖。

原因：这些文件下次启动会被**整份**读回来解析。`fs::write` 先截断再写，崩在半路就留下
"看起来像 JSON 但只有一半"的文件，于是设置悄悄回退默认值——一个只在断电时出现的 bug，
比一个每次出现崩溃的 bug 难得多。

临时文件是同目录的兄弟，不是系统临时目录：`rename` 只在同一个文件系统内原子，跨盘就变成复制。

改名覆盖的 `set` 是"读-改-写"，所以进程内串行（`OnceLock<Mutex<()>>`）并在锁内**重读**文件：
否则两个窗口同时改名，后写的那个会拿着旧表把前一个改名抹掉。

### 删掉一个会话会发生什么

`session_delete` 把整个会话目录 **`rename` 到 `<dsh_home>/trash/<id>-<时间戳>/`**，然后清掉它的
改名覆盖。理由很实际：删除按钮离"点错了行"只有一个回车键的距离，而 `rename` 是可逆的。

`session_purge` 才是 `remove_dir_all`。界面上应该是两层：先删除（进回收站），真删要另一次
确认，并且说清"这个不能再恢复"。

回收站目前**没有自动清理**，也没有还原命令——需要还原的人直接把目录搬回
`sessions/<project>/` 即可。这是有意的：自动清空一个叫"回收站"的目录，等于把可恢复做成不可恢复。

### 会话从磁盘重新打开

`session/prompt` 之前如果这个 id 在 store 里存在、而当前内核不认识它，客户端先发
`session/resume`（失败只 warn，不阻断——resume 是礼貌，不是门禁）。

### 日志

`<dsh_home>/logs/desktop.log.<YYYY-MM-DD>`（rolling appender 会加日期，精确匹配
`desktop.log` 找不到文件）。**同步写**：non-blocking 在被强杀时丢缓冲，而崩溃日志正是唯一需要它的时候。

### 构建被锁

Windows 上常驻程序会持有刚写出的 exe，症状是 `LNK1104`。
`node scripts/handles.mjs <path>` 点名占用者；绕法是
`CARGO_TARGET_DIR=D:/dsh-build-target cargo build --release -p dsh-desktop-app`，
`scripts/smoke-app.mjs` 会自动去那里找二进制。
